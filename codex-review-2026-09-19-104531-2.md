# Sigil Code, Security, and Post-Quantum Review

Generated: 2026-09-19 10:45:31 Europe/Sofia

## Overall verdict

Sigil is a strong thesis/MVP codebase with good test coverage and generally modern PHP practices. Production readiness is blocked by document-access and deadline-enforcement bugs, alongside transactional, audit-integrity, deployment, and cryptographic-agility issues. This is an engineering assessment, not a determination of legal or qualified-signature status.

Validation reported by the original review:

- Full suite completed successfully: 175 tests, 1,794 assertions, 11 skipped.
- Unit-only suite: 26/26 passed.
- PHPStan level 8: no errors.
- PHP, YAML, and Twig linting passed.
- Composer found no known security advisories.
- The complete suite needed a 512 MiB PHP memory limit because of mPDF.
- No source files were changed as part of the review.

Independent verification during the follow-up comparison:

- Unit suite rerun successfully: 26 tests, 39 assertions.

- The owner-grant deletion finding below was established by tracing the controller, service, repository, and download paths; it was not reproduced against persisted data.
- Runtime inspection reconfirmed pyHanko 0.35.2, `cryptography` 49.0.0, and SoftHSM 2.6.1, with no advertised ML-DSA mechanisms.
- Official Symfony and pyHanko release information and RFCs 9881/9882 were checked.

## Highest-priority updates

### 1. Preserve the owner's decryption grants when closing a signing request [P1]

[`src/Signing/Controller/SigningRequestController.php`](src/Signing/Controller/SigningRequestController.php) explicitly supports including the owner in the signer queue. However, `SigningRequestService::close()` deletes every document grant belonging to the current unsigned signer, without exempting the owner. Cancellation, decline, or expiry while the owner holds the turn therefore removes the owner's existing decryption grants.

The deletion is performed by [`DocumentKeyGrantRepository::deleteForDocumentAndUser()`](src/Document/Repository/DocumentKeyGrantRepository.php). [`DocumentDownloader::download()`](src/Document/Service/DocumentDownloader.php) requires a grant even for the owner, so ownership alone does not restore access.

Preserve ownership-based access when revoking signing-turn access. Add regression coverage for the owner holding the turn during cancellation, decline, and expiry, including a partially signed document. This is a deterministic authorization/lifecycle bug that transactions alone will not fix.

### 2. Make signing, delivery, cancellation, and grant changes transactional and concurrency-safe

[`src/Delivery/Service/DeliveryService.php`](src/Delivery/Service/DeliveryService.php) marks and flushes a delivery before granting recipients access. A grant failure therefore contradicts the stated “all or nothing” invariant. Similar windows exist around signing-request state transitions.

For example, [`DocumentSigner`](src/Signing/Service/DocumentSigner.php) persists the signed version through `DocumentVersionWriter` before recording the signature and advancing the request. [`SigningRequestService`](src/Signing/Service/SigningRequestService.php) also flushes request creation before granting the first signer access, and closes requests before deleting the current signer's grants.

Existing protection should be retained: [`DoctrineAuditLogger`](src/AuditLog/Service/DoctrineAuditLogger.php) already appends inside a transaction with a PostgreSQL advisory lock, and unique constraints already protect document-version numbers, per-version grants, and signer positions/users. These controls do not make the enclosing business workflows atomic. Delivery and signing-request creation still lack a unique document constraint enforcing their stated one-per-document invariant.

Recommended controls:

- Doctrine transactions around related database mutations.
- Pessimistic locking or optimistic version columns on terminal state transitions.
- Additional unique database constraints for the one-delivery and one-signing-request-per-document invariants, retaining existing constraints.
- After-commit events or a transactional outbox.
- Compensation for object-storage and PKCS#11 operations that cannot participate in the database transaction.

### 3. Enforce the deadline in the signing path [P2]

[`SigningRequest::isTurnOf()`](src/Signing/Entity/SigningRequest.php) checks pending status and signer identity, but not the deadline. [`DocumentSigner::assertMaySign()`](src/Signing/Service/DocumentSigner.php) relies on this predicate, and `SigningRequestService::recordSignature()` does not add a deadline check.

Consequently, an overdue pending request remains signable until [`SweepSigningRequestsCommand`](src/Signing/Command/SweepSigningRequestsCommand.php) expires it. An in-memory probe confirmed that a request with yesterday's deadline reports both `isOverdue() === true` and `isTurnOf() === true` for its current signer.

Enforce the deadline using the injected clock during signing authorization and define how signatures in flight at the deadline are handled. Revalidate state at the commit boundary alongside concurrency controls. Keep the sweep for cleanup rather than relying on its schedule to enforce authorization.

### 4. Fix trusted-host validation and review absolute-URL handling

[`config/packages/framework.yaml`](config/packages/framework.yaml) has no `trusted_hosts`, while verification and notification emails create absolute URLs, for example in [`src/Auth/Service/EmailVerifier.php`](src/Auth/Service/EmailVerifier.php).

This permits Host-header poisoning if the reverse proxy does not independently constrain the host. Configure `trusted_hosts`. A default URI already exists in [`config/packages/routing.yaml`](config/packages/routing.yaml), through `%env(DEFAULT_URI)%`; ensure its production value is canonical. That setting supplies URL context outside HTTP requests and does not itself validate or replace an incoming request's host. See Symfony's [trusted-hosts documentation](https://symfony.com/doc/current/reference/configuration/framework.html#trusted-hosts).

### 5. Strengthen the audit log

[`src/AuditLog/Entity/AuditLogEntry.php`](src/AuditLog/Entity/AuditLogEntry.php) uses an unkeyed SHA-256 chain. SHA-256 is not the problem: an attacker with database write access can rewrite entries and recompute the chain, or delete its tail without recomputing anything. The verifier has no independent expected head or length.

Periodically sign or HMAC the chain head and publish or store that checkpoint outside the database—ideally in immutable/WORM storage or an external timestamp service.

### 6. Fix certificate-revocation recovery

The database is committed before the token is deleted in [`src/Certificate/Service/CertificateIssuer.php`](src/Certificate/Service/CertificateIssuer.php). If token deletion fails, the certificate is already marked revoked and retrying is rejected; the revocation audit call is also skipped. The application's signing gate rejects the revoked certificate, so the failure concerns token cleanup and audit completeness, not automatic restoration of signing access.

Keep revocation effective immediately and make token cleanup idempotent and retryable, with durable tracking of pending/failed cleanup and an audit record of the revocation decision. A separate cleanup status/job is sufficient; a new `revocation_pending` certificate status is optional and must remain unusable for signing.

### 7. Reconsider permissive PDF parsing

[`bin/sign_pdf.py`](bin/sign_pdf.py) uses `strict=False` for hybrid cross-reference PDFs. Signing exact bytes does not eliminate parser-confusion attacks: two PDF viewers may render the same signed bytes differently.

Define an admission policy for ambiguous PDFs, including rejection where appropriate. Canonicalization must account for existing signatures: this application supports previously signed input, as exercised in [`DocumentSigningE2ETest`](tests/Functional/Signing/DocumentSigningE2ETest.php). Rewriting such a PDF can invalidate or discard its existing signatures. If conversion is supported, preserve the original and make the converted PDF an explicit derivative with an audit record and clear treatment of prior signatures. Strict parsing alone is not proof against every rendering ambiguity.

### 8. Protect authentication secrets better

The TOTP seed is a plaintext database column in [`src/Core/Entity/User.php`](src/Core/Entity/User.php). Encrypt it using the existing envelope-encryption facility.

Also implement `User::__serialize()` so the real password hash and TOTP secret are not serialized into the session. Symfony recommends protecting password hashes stored in sessions in its [security guidance](https://symfony.com/doc/current/security.html#understanding-how-users-are-refreshed-from-the-session).

### 9. Correct the receipt's digest claim

[`templates/receipt/delivery_receipt.html.twig`](templates/receipt/delivery_receipt.html.twig) labels the document fingerprint as “SHA-384”, but [`ContentHasher`](src/Document/Service/ContentHasher.php) computes HMAC-SHA-384 under a root-derived secret key. A recipient cannot reproduce this value with an ordinary SHA-384 checksum or verify it independently without access to the key or a verification service.

Correct the receipt label and explain what the fingerprint can verify. This is a user-visible evidence-description issue, not just a stale code comment. If independent document-to-receipt verification is required, design that capability explicitly while preserving the confidentiality rationale for avoiding plaintext hashes in leaked database rows.

## Symfony and PHP quality

Most practices are good:

- PHP 8.4 and `strict_types`.
- Typed and readonly dependencies.
- Attributes, enums, constructor injection, and PSR clocks.
- Forms and CSRF protection.
- Login throttling, 2FA, and certificate-PIN rate limits.
- Parameterized Doctrine queries.
- Versioned crypto identifiers and self-describing encryption envelopes.
- Automatic password hashing and password migration.
- Solid test and static-analysis configuration.

However, [`composer.json`](composer.json) pins Symfony `8.0.*`. Symfony 8.0 support ended in July 2026. Upgrade the constraints to Symfony 8.1 and run the deprecation suite first. See the [Symfony 8.0 release status](https://symfony.com/releases/8.0).

Dependency auditing already exists: [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs `composer audit` before PHPStan and the tests. Retain that check; any expanded auditing should identify additional scope, such as Python dependencies or container packages, rather than treating Composer auditing as missing.

For production, provide a separate hardened deployment definition. The current [`compose.yaml`](compose.yaml) is development-oriented: `APP_ENV=dev`, development fallback secrets, `latest` image tags, exposed databases, HTTP, and PHP's built-in server.

## Repeating code

Duplication is noticeable but manageable:

- `currentUser(): User` is copied into eight controllers.
- UUID equality through repeated `toRfc4122()` calls appears throughout the application.
- Authorization and load-or-404 logic are duplicated across controllers.
- PHP-to-Python process execution and JSON error handling are repeated in the pyHanko, certificate, and root-key drivers.
- UTC clock conversion is repeated.
- Multi-step workflows repeatedly perform “mutate → flush → audit → dispatch,” but without one consistent transaction abstraction.

Recommended refactoring:

- Symfony voters for document, certificate, delivery, and signing-request authorization.
- `User::sameIdentityAs()` or an identity value object.
- A typed authenticated-user provider.
- One hardened JSON subprocess gateway.
- An application transaction/outbox coordinator.

There is also stale terminology: [`src/Document/Entity/DocumentVersion.php`](src/Document/Entity/DocumentVersion.php) says `contentHash` is plain SHA-384, but the implementation is now keyed HMAC-SHA-384. Rename it to `contentMac` or update the comments and invariants accordingly. Correcting the receipt's public-facing digest claim is a separate priority above; a field rename alone does not resolve it.

## Cryptographic assessment

| Mechanism | Classical/2030 assessment | Post-quantum assessment |
|---|---|---|
| AES-256-GCM | Strong; correct 256-bit keys, 96-bit random nonces, and AAD | Strong practical PQ margin |
| HKDF-SHA-256 | Strong | Approximately 128-bit PQ margin; sufficient |
| HMAC-SHA-384 | Strong | Strong PQ margin |
| SHA-256 audit chain | Hash is safe; construction is not externally tamper-evident | Hash remains usable, but anchoring problem remains |
| Argon2id certificate PINs | Good | Appropriate, but costs should be calibrated and `password_needs_rehash()` added |
| Symfony `auto` password hashing | Appropriate and migration-aware | Password strength and cost dominate; consider calibrated Argon2id for this high-value application |
| ECDSA P-384/SHA-384 | Strong against classical attacks | Not post-quantum |
| RSA-3072/SHA-384 | Strong against classical attacks | Not post-quantum |
| Dev TSA ECDSA P-256 | Classically acceptable | Not post-quantum |

No broken primitive such as MD5, unauthenticated encryption, or bare SHA-1 was found in the application's protection paths.

NIST explicitly states that RSA and ECDSA are not expected to resist a large quantum computer. Its current transition guidance targets removal of quantum-vulnerable algorithms by 2035, with high-risk systems moving earlier. That does not mean ECDSA suddenly breaks in 2030, but it is unsuitable for evidence expected to remain trustworthy well beyond that date.

Sources:

- [NIST PQC migration guidance](https://csrc.nist.gov/projects/post-quantum-cryptography)
- [NIST's classical-signature assessment](https://csrc.nist.gov/news/2023/nist-releases-fips-186-5-and-sp-800-186)

There is no absolute “quantum proof.” ML-DSA is described as *believed* resistant based on current knowledge. See [NIST FIPS 204](https://csrc.nist.gov/pubs/fips/204/final).

### Encryption and hashing details

The symmetric encryption design is generally sound:

- [`src/Core/Crypto/AesGcmSodiumCipher.php`](src/Core/Crypto/AesGcmSodiumCipher.php) uses AES-256-GCM through libsodium and fails closed when the implementation is unavailable.
- [`src/Core/Crypto/EnvelopeEncryptionService.php`](src/Core/Crypto/EnvelopeEncryptionService.php) generates random nonces and authenticates the envelope version, algorithm identifier, and caller AAD.
- The key hierarchy uses a root wrapping key, per-user KEKs, and per-version DEKs.
- Sensitive temporary key values are generally cleared with `sodium_memzero()`.
- Document fingerprints use keyed HMAC-SHA-384, avoiding a plaintext confirmation oracle after a combined database and object-storage leak.

Operationally, AES-GCM nonce uniqueness still matters. The current 96-bit random nonces are appropriate for this system's expected scale, especially because document DEKs are fresh, but invocation counts per long-lived KEK should remain bounded and monitored.

Certificate PINs are hashed with Argon2id, which is appropriate. The implementation should nevertheless:

- set and benchmark explicit memory, time, and thread costs;
- call `password_needs_rehash()` after successful verification;
- centralize PIN hashing rather than invoking `password_hash()` in multiple locations.

## Can Sigil use ML-DSA through pyHanko?

Yes—technically it is now feasible, but it is not a configuration-only change.

Current standards and library support are substantially better than they were previously:

- ML-DSA is standardized by NIST in FIPS 204.
- X.509 encoding is standardized by [RFC 9881](https://www.rfc-editor.org/rfc/rfc9881.html).
- CMS encoding, which PDF/PAdES uses, is standardized by [RFC 9882](https://www.rfc-editor.org/rfc/rfc9882.html).
- pyHanko 0.35.1 added ML-DSA signing and verification.
- pyHanko 0.36 added ML-DSA through its PKCS#11 signer.

See the [pyHanko release history](https://docs.pyhanko.eu/en/latest/changelog.html).

[`Dockerfile`](Dockerfile) pins pyHanko 0.37.0, which is suitable. However, the container running during the review was stale:

- running pyHanko: 0.35.2;
- running `cryptography`: 49.0.0;
- running SoftHSM: 2.6.1;
- the SoftHSM module exposed no `CKM_ML_DSA` mechanism.

The follow-up runtime inspection reconfirmed these versions and the absence of advertised ML-DSA mechanisms. It did not rebuild or replace the container.

Therefore, `docker compose up --build` is needed just to obtain the pinned pyHanko. The Alpine SoftHSM package must also be replaced with a current ML-DSA-enabled build or an ML-DSA-capable hardware HSM.

PKCS#11 3.2 now standardizes `CKM_ML_DSA` and ML-DSA key generation. See [OASIS PKCS#11 3.2](https://docs.oasis-open.org/pkcs11/pkcs11-spec/v3.2/pkcs11-spec-v3.2.html).

### Current algorithm-agility gap

The PHP layer appears algorithm-agile, but the complete signing path is not:

- [`bin/sign_pdf.py`](bin/sign_pdf.py) hard-codes SHA-384 and ECDSA.
- Its `PKCS11Signer` construction hard-codes the ECDSA signature mechanism.
- [`bin/issue_cert.py`](bin/issue_cert.py) hard-codes the issuer signature suite.
- Consequently, even the existing PHP `RSA-3072-SHA384/v1` option is not genuinely supported end-to-end.

The algorithm choice needs to travel from PHP into certificate issuance and document signing. The descriptor should distinguish:

- key family and parameter set;
- PKCS#11 key-generation mechanism;
- CMS digest algorithm;
- X.509 signature algorithm;
- raw, pre-hashed, or pure signing mode;
- expected public-key and signature sizes.

ML-DSA's pure signing mode must not be forced through the existing ECDSA “hash first, then raw token signature” behavior. RFC 9882 specifies that, when CMS signed attributes are present, pure ML-DSA signs their complete DER encoding. The content digest is carried in the message-digest attribute; SHA-384 is an allowed content digest for ML-DSA-65. The content-digest choice and the token's signing mode are separate decisions.

## Recommended ML-DSA migration

Use ML-DSA-65 as the balanced default PQ suite while retaining ECDSA P-384 during migration.

1. Make the algorithm selection travel from PHP into both Python drivers.
2. Add ML-DSA-65 key generation, X.509 issuance, CMS signing, and validation.
3. Upgrade or replace SoftHSM with a `CKM_ML_DSA` implementation.
4. Establish an ML-DSA CA; an ML-DSA leaf under an ECDSA-signed CA is not end-to-end quantum-resistant.
5. Initially add separate ECDSA and ML-DSA signatures to the PDF. Composite/hybrid CMS work is newer and less interoperable.
6. Upgrade from PAdES-B-T toward B-LTA with renewable archive timestamps.
7. Include the application seal, TSA, certificate chain, revocation evidence, and validation service in the PQ migration—not only user signatures.
8. Test pyHanko validation plus the actual PDF viewers and trust environments used by recipients.

This would be a strong thesis extension. It can deliver a real standards-based PQ proof of concept, but NIST standardization and pyHanko support do not automatically guarantee Adobe viewer compatibility, ETSI/eIDAS acceptance, qualified-signature status, or support from deployed hardware tokens.

## Final assessment

The application demonstrates thoughtful security design: authenticated encryption, key separation, non-exportable token keys, PIN gating, versioned algorithms, controlled document grants, audit records, and extensive tests. Its immediate correctness risks include owner-access deletion, unenforced signing deadlines, partial workflow commits, and unrecoverable token-cleanup failures. Audit anchoring, receipt verification semantics, PDF admission, deployment hardening, and the gap between PHP algorithm descriptors and the Python signing implementation also need attention.

Addressing those issues before adding ML-DSA will provide a much stronger foundation. ML-DSA can then be added through pyHanko as a genuine end-to-end suite rather than as an isolated signature primitive.

## Cryptographic interchangeability and service boundaries

Not every hash, encryption mechanism, or signature algorithm is currently interchangeable through a new service and an alias in the way that object-storage backends are interchangeable.

Storage does not actually switch between MinIO and AWS through a single Symfony alias. It uses tagged backends, an environment-selected active backend, and a stable backend ID embedded in every storage key. That final property is what keeps old objects readable after new writes move to another backend.

| Area | Interchangeable now? | Notes |
|---|---:|---|
| MinIO/AWS/local storage | Yes | Active backend comes from the environment; old keys route to their original backend |
| TSA provider | Yes | Tagged registry with an environment-selected active provider |
| PAdES implementation | Yes | `PadesSignerInterface` can be aliased to pyHanko, CSC, SetaPDF, or another implementation |
| AES document encryption | Partially | Algorithms are registered and envelopes identify their algorithm, but the active algorithm is hard-coded |
| Root-key wrapping | Partially | The implementation can be aliased, but historical wrapper formats are not transparently routed |
| Signature algorithm | No | PHP has a registry, but the Python implementation hard-codes ECDSA |
| Content HMAC and KDF | No | HKDF-SHA-256 and HMAC-SHA-384 are hard-coded |
| Audit hash | No | SHA-256 is called directly in the entity and verifier |
| User-password hashing | Mostly | Symfony `auto` supports algorithm migration and rehashing |
| Certificate-PIN hashing | No | Direct `password_hash(..., PASSWORD_ARGON2ID)` calls are used |

### Symmetric encryption: close, but not fully configurable

This part has the best crypto-agility design.

Business code uses [`src/Core/Crypto/EncryptionServiceInterface.php`](src/Core/Crypto/EncryptionServiceInterface.php), and cipher implementations are automatically tagged through [`src/Core/Crypto/CipherAlgorithmInterface.php`](src/Core/Crypto/CipherAlgorithmInterface.php).

Every encrypted envelope contains its stable algorithm ID, so old ciphertext can remain decryptable after a new cipher is introduced. The limitation is that the active cipher is hard-coded in [`src/Core/Crypto/CipherAlgorithmRegistry.php`](src/Core/Crypto/CipherAlgorithmRegistry.php):

```php
public function default(): CipherAlgorithmInterface
{
    return $this->get(AesGcmSodiumCipher::ID);
}
```

Adding a new cipher currently requires:

1. Implementing `CipherAlgorithmInterface`.
2. Changing `default()`.
3. Keeping the old implementation registered indefinitely.
4. Checking key-size compatibility throughout the existing key hierarchy.

The registry should accept an environment-backed active ID such as `SIGIL_CIPHER_ACTIVE_ALGORITHM`, following the pattern in `StorageBackendRegistry`.

The key hierarchy currently assumes 32-byte KEKs and DEKs. A new 32-byte-key cipher would fit the existing design easily. An algorithm with a different key size would require versioned key material and an explicit migration plan.

### Hashes, MACs, and KDFs: hard-coded

[`src/Core/Crypto/EnvelopeEncryptionService.php`](src/Core/Crypto/EnvelopeEncryptionService.php) directly implements:

```php
hash_hkdf('sha256', ...);
hash_hmac('sha384', ...);
```

Adding a new `CipherAlgorithmInterface` therefore does not change the KDF or MAC.

More importantly, document `contentHash` values do not store an algorithm identifier. If HMAC-SHA-384 were replaced, the application would not know which algorithm should verify an old database row.

A safe representation would be self-describing:

```text
HMAC-SHA384/v1:<hex digest>
```

Alternatively, use separate columns:

```text
content_integrity_algorithm
content_integrity_value
```

The responsibilities could be divided into:

- `EnvelopeEncryptionInterface`
- `KeyDerivationInterface`
- `MacInterface`

Alternatively, the existing service can remain, but its KDF and MAC operations should use versioned registries and produce self-describing values.

### Audit hashing: not interchangeable

SHA-256 is directly invoked in:

- [`src/AuditLog/Entity/AuditLogEntry.php`](src/AuditLog/Entity/AuditLogEntry.php)
- [`src/AuditLog/Command/AuditVerifyCommand.php`](src/AuditLog/Command/AuditVerifyCommand.php)

Changing one without the other would break verification. There is no algorithm version stored with the chain.

An `AuditChainHasherInterface` would centralize the operation, but algorithm abstraction alone would not fix the more important anchoring weakness. Each audit-chain epoch should record its scheme and have an externally stored or cryptographically signed checkpoint.

### Root-key wrapping: aliasable, but not transparently migratable

The application can alias [`src/Core/Crypto/RootKeyWrapperInterface.php`](src/Core/Crypto/RootKeyWrapperInterface.php) to either `Pkcs11RootKeyWrapper` or `EnvRootKeyWrapper`. The test environment already performs such an override in [`config/services.yaml`](config/services.yaml).

However, each implementation rejects the other implementation's scheme byte. There is no routing facade equivalent to:

```text
0x01 -> EnvRootKeyWrapper
0x02 -> Pkcs11RootKeyWrapper
```

Switching aliases therefore requires the root-key migration command to rewrite the stored KEKs.

To make this equivalent to object storage, introduce:

- tagged `RootKeyWrapperInterface` implementations;
- stable scheme IDs;
- an active wrapper for new writes;
- a routing wrapper that selects the matching historical implementation for reads.

### Digital signatures: not currently interchangeable

The PHP layer appears algorithm-agile:

- certificates persist an `algorithmId`;
- algorithms implement `SignatureAlgorithmInterface`;
- `SignatureAlgorithmRegistry` discovers tagged implementations.

However, its default is hard-coded to ECDSA, and the selected algorithm does not travel through the complete Python signing path.

[`bin/sign_pdf.py`](bin/sign_pdf.py) hard-codes:

```python
MD_ALGORITHM = "sha384"
ECDSA_SIG_MECHANISM = ...
```

Its `PKCS11Signer` construction always uses that ECDSA mechanism. [`bin/issue_cert.py`](bin/issue_cert.py) similarly hard-codes the issuer signature suite.

Consequently:

- adding an ML-DSA PHP service is insufficient;
- changing the signature registry default is insufficient;
- the existing PHP `RSA-3072-SHA384/v1` descriptor is not genuinely supported end-to-end for PDF signing.

The algorithm ID must be added to `PadesSignRequest`, passed through `PyHankoAdapter`, sent to Python, and resolved there into the appropriate X.509, CMS, digest, and PKCS#11 behavior.

### Passwords and certificate PINs

User-password hashing is reasonably interchangeable through Symfony's password-hasher configuration. `UserRepository` implements password upgrading, so changing the configured algorithm can rehash passwords after successful authentication.

Certificate PINs are different. Argon2id is invoked directly during certificate issuance and PIN changes, while `PinGate` calls `password_verify()` directly.

A dedicated certificate-PIN hasher should centralize:

```php
hash()
verify()
needsRehash()
```

This would make cost and algorithm changes safe, consistent, and testable.

### Target architecture

For persistent cryptographic material, simply changing a service alias is unsafe because historical data may immediately become unreadable or unverifiable. The desired model is:

```text
                       active algorithm
                              |
                              v
new write ----------------> registry
                              |
                  stores stable algorithm ID
                              |
old read ---- reads ID -------+
                              |
                              v
                 matching historical implementation
```

Recommended changes:

1. Make cipher and signature defaults environment-configurable.
2. Add algorithm IDs to content MACs and audit-chain epochs.
3. Add a root-wrapper registry and routing facade.
4. Centralize certificate-PIN hashing and rehash checks.
5. Pass the certificate algorithm through the complete PHP-to-Python boundary.
6. Retain historical algorithms for reading and verification.
7. Add migration commands where key lengths or stored formats change.
8. Add compatibility tests that create data under algorithm A, switch new writes to B, and still read or verify artifacts created with A.

In summary, document encryption is already close to the MinIO/AWS model, but signatures, hashes, MACs, certificate PINs, and root-key wrappers are not yet uniformly interchangeable.
